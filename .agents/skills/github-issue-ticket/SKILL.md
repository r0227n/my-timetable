# GitHub Issue Ticket

発見事項を、再現・検証可能で重複のないIssueへ変換する。`docs/SPEC.md`、Issue Forms、ラベル定義をそれぞれのSSOTとして扱う。

## 必ず読むファイル

作業開始時に `docs/SPEC.md` の関連箇所、`.github/ISSUE_TEMPLATE/bug.yml`、`.github/ISSUE_TEMPLATE/feature.yml`、`.github/labels.yml` を読む。ファイルがない、またはYAMLが不正な場合は起票しない。

## 分類と本文

- `bug`: 観測結果が `docs/SPEC.md` の明確な要件と異なる。
- `feature`: 仕様にない新しい振る舞い、または既存機能の改善を求める。
- 仕様が曖昧、証拠が不十分、分類に確信が持てない場合は推測せず、ユーザーへ判断を求める。

タイトルは日本語で対象と事象または要求が分かるようにし、`[Bug]` や `[Feature]` は付けない。コード識別子、ログ、エラーは原文を維持する。

該当するIssue Formの `body` の順序、ラベル、必須項目を読み、その構造に対応するMarkdown本文を作る。フォームにない必須知識を別の固定書式として複製しない。Agentが発見した事項には発見日時、実際の検証、信頼度を記載し、`agent-created` を追加する。人間から渡された事項には根拠なくAgent情報やラベルを付けない。

ローカルファイルを外部へアップロードしない。公開済みURL、既存のGitHub添付URL、再現手順、観測結果を証拠として使い、URLがなければその旨を記載する。

## 重複確認

起票前に `gh repo view` で対象を確認し、`gh issue list --state all` でOpen・Closedの両方を検索する。タイトルだけでなく、同じ画面・機能、期待結果、症状・要求、利用者から見た完了条件を比較する。原因が異なっても完了条件が同じなら重複候補とする。

候補が1件でもあれば新規起票を停止し、Issue番号、タイトル、URL、一致理由を提示する。既存Issueへ自動でコメントしない。追記を指示された場合だけコメント案を示し、外部変更の承認後に投稿する。

## ラベルと起票

`gh label list` で必要なラベルを確認する。存在しないものだけ `.github/labels.yml` の色と説明で作成し、既存ラベルは変更しない。定義にないラベルを推測で作らない。

通常は外部変更前に、対象リポジトリ、種別、タイトル、本文、付与ラベル、新しく作成するラベルの色・説明をまとめて提示し、明示的な承認を待つ。承認後、欠けたラベルを作成し、`gh issue create` でIssueを1件作成する。失敗時に内容を変えて繰り返さず、原因と外部状態を報告する。

無人起票は、呼び出し元がこの実行の外部変更を事前承認済みであり、`auto-submit` を明示した場合だけ許可する。単なる語の言及、スケジュール実行、過去の承認から権限を推測しない。自動モードでも、重複候補、分類不明、仕様不明、必須項目不足なら起票しない。

## 完了報告

Issue番号、タイトル、URL、付与したラベル、新規作成したラベルを報告する。起票しなかった場合は理由と、人間が判断すべき事項を報告する。

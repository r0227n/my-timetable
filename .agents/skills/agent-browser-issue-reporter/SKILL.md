# Agent Browser Issue Reporter

agent-browserによる動作確認とIssue候補の発見を一つの流れとして扱う。動作確認の依頼範囲を広げず、Issueの分類・重複確認・書式・ラベル・起票判断は`github-issue-ticket`へ委ねる。

## 動作確認

1. `docs/SPEC.md`の対象フローを読み、期待結果と確認範囲を定める。
2. `agent-browser`を読み、実行前にCLIから`core`を取得する。QA、探索的テスト、バグ探索では`dogfood`も取得し、その手順で実画面を操作する。
3. 主要フロー、入力、エラー表示、画面遷移のうち依頼に関係する範囲を確認する。

気になる挙動を観測した時点で、次の情報を保持する。

- 初期状態からの再現操作
- 期待結果と、その根拠になる仕様の節。仕様にない改善案では具体的な利用者課題
- 実際の表示、状態、エラー原文
- URLまたはルート、OS、ブラウザ、端末、関連する機能状態
- 実施した再確認と結果、発見日時、信頼度
- 公開済みの証拠URL。ローカルのスクリーンショットやファイルはアップロードせず、公開URLがなければその旨

安全に再現できる挙動は、初期状態へ戻して最小手順でもう一度確認する。一度だけの揺れや主観的な違和感は、再現または具体的な利用者課題を確認できるまでIssue候補にしない。データ消失、セキュリティ、プライバシー侵害など継続操作に危険がある場合は直ちに操作を止め、観測済みの情報だけを報告する。それ以外は発見後も依頼された動作確認を続ける。

## 発見事項の引き渡し

動作確認後、次のゲートを満たす発見事項だけをIssue候補にする。

- 再現可能な観測事実がある。
- 仕様との差、または具体的な利用者課題を説明できる。
- 独立した完了条件を記述できる。

ゲートを満たさない事項は「要追加調査」として、足りない証拠と次に確認すべき内容を報告する。異なる完了条件を持つ候補は分割し、候補ごとに`github-issue-ticket`を使用する。同Skillに、仕様との照合、`bug`または`feature`への分類、Issue Formsへの整形、Open・Closed Issueとの重複確認、ラベル確認、承認、起票を任せる。

外部変更は`github-issue-ticket`の承認境界に従う。この実行についてユーザーが`auto-submit`を明示していない限り、Issue案を提示して承認を待つ。過去の承認や動作確認の依頼から自動起票の権限を推測しない。

## 完了条件

依頼範囲の動作確認結果、Issue候補、要追加調査を報告する。候補がなければ、確認したフローと「起票候補なし」を明記する。候補がある場合は、各候補が`github-issue-ticket`によって起票済み、重複、承認待ち、または判断待ちのいずれかになった時点で完了する。

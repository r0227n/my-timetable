# タイムテーブル抽出・マイタイムライン作成Webアプリ 仕様書

## 1. 文書情報

| 項目 | 内容 |
|---|---|
| 文書名 | タイムテーブル抽出・マイタイムライン作成Webアプリ 仕様書 |
| 想定バージョン | MVP 1.0 |
| フロントエンド | React + Vite + TypeScript |
| ホスティング | GitHub Pages |
| バックエンド | なし |
| AI実行方式 | ブラウザ内推論（WebGPU優先、対応可能な処理のみWASMへフォールバック） |
| データ保存 | 作業データは保存しない。最小限のUI設定のみlocalStorageへ保存 |

## 2. 目的

ユーザーがイベントのタイムテーブル画像をアップロードし、ブラウザ内で文字・表構造を抽出する。抽出結果から出演者を自由に選択し、個人用タイムライン画像の生成、ICSファイルの出力、またはGoogle Calendarへの登録を行えるWebアプリを提供する。

サーバーへの画像送信やユーザーデータの保存は行わない。

## 3. 前提条件と制約

### 3.1 GitHub Pages

- アプリは静的なHTML、CSS、JavaScriptとして配信する。
- Node.js、Python、Ollama、vLLMなどのサーバープロセスは使用しない。
- GitHub Pagesのプロジェクトサイト配下でも動作するよう、Viteの `base` をリポジトリ名に合わせて設定する。
- SPAの深いURLへ直接アクセスすると404になる問題を避けるため、MVPは単一ページ構成とする。

### 3.2 AIモデル

- GLM-OCRとGemmaはユーザー端末のブラウザ内で実行する。
- GLM-OCRはブラウザ互換形式へ変換・量子化されたONNXモデルを使用する。
- Gemma 4はブラウザ向け小型・量子化モデルを使用する。初期値はE2Bとし、WebGPU対応かつ `navigator.deviceMemory` が8GB以上の場合のみE4Bを選択可能にする。端末メモリを取得できない場合はE4Bを利用不可とする。
- 推論ランタイムはWebGPU対応のONNX Runtime Webまたは採用モデルと互換性のあるWebGPUランタイムを使用する。
- GLM-OCRの公式サーバー実装をそのままGitHub Pages上で動かすことはできないため、ブラウザ変換版の精度・互換性を事前検証する。
- モデルファイルはGitHub Pagesリポジトリへ格納しない。Hugging Face、CDN、または静的オブジェクトストレージから取得する。
- 使用するモデル、変換物、フォント、ライブラリのライセンスを公開前に確認し、必要な表示を行う。

### 3.3 対応端末

- 推奨対象はWebGPU対応の最新版ChromeまたはEdgeを搭載したPCとする。
- Safari、Firefox、スマートフォンはベストエフォート対応とする。
- WebGPU非対応時は、AI処理を実行できない旨と推奨環境を表示する。
- WASMへの全面フォールバックは速度とメモリ消費の観点から必須要件としない。

### 3.4 セキュリティとプライバシー

- アップロード画像と抽出データを外部サーバーへ送信しない。
- 画像、認識結果、選択内容は原則として端末内だけで処理する。
- Google OAuthのアクセストークンを永続保存しない。メモリ内で保持し、ページ終了または有効期限切れで破棄する。
- AIサービス用の秘密APIキーは使用しない。静的JavaScript内に秘密情報を埋め込まない。

## 4. 対象範囲

### 4.1 MVPに含める機能

1. タイムテーブル画像のアップロード
2. 画像のプレビュー、回転、切り抜き、縮小
3. GLM-OCRによる文字・レイアウト抽出
4. Gemmaによる構造化JSONへの整形
5. 抽出結果の確認と手動修正
6. 出演者・予定の選択
7. 時間重複の検出
8. 個人用タイムラインのプレビュー
9. SVGおよびPNG画像の保存
10. ICSファイルの保存
11. Google Calendarへの直接登録
12. 必要最小限のUI設定保存

### 4.2 MVPに含めない機能

- ユーザーアカウント
- クラウド同期
- 複数端末間のデータ共有
- サーバー側での画像・モデル処理
- 公開共有URL
- 運営者によるタイムテーブル管理画面
- 課金、利用回数管理
- OCR結果のサーバー収集や学習利用

## 5. ユーザーフロー

1. ユーザーがトップ画面を開く。
2. アプリがWebGPU、利用可能メモリ、ブラウザ機能を確認する。
3. ユーザーがヘッダーで現在のGemmaモデルを確認し、必要に応じてE2Bまたは利用可能なE4Bを選択する。
4. ユーザーがタイムテーブル画像を選択する。
5. ユーザーが必要に応じて画像を回転・切り抜きする。
6. 初回のみ、必要なAIモデルを外部配信元からダウンロードする。
7. GLM-OCRが画像内の文字と位置情報を抽出する。
8. 解析開始時に選択されていたGemmaがOCR結果を所定のJSON形式へ整形する。
9. ユーザーが要確認の予定を中心に、イベント日、時刻、出演者名などを元画像と照合して修正し、確認済みにする。
10. 入力不備のない確認済み予定から、参加したい出演者または個別予定を選択する。未確認予定は選択対象外とする。
11. アプリが時間の重複や移動余裕時間の不足を警告する。
12. ユーザーがタイムラインの色、レイアウト、表示項目を調整する。
13. ユーザーがPNG/SVG、ICS、またはGoogle Calendar登録を選択する。

## 6. 画面仕様

### 6.1 トップ・アップロード画面

#### 表示項目

- アプリ名と簡単な説明
- 「画像を選択」ボタン
- クリック、ドラッグ＆ドロップ、クリップボード貼り付けに対応する画像入力領域
- 対応形式・推奨端末の表示
- 「画像は端末外へ送信されません」の案内
- WebGPU対応状況
- モデルダウンロード容量の事前表示
- ヘッダーの現在選択中Gemmaモデル名とモデル選択メニュー
- E4Bが利用不可の場合の非活性表示と理由
- モデル変更は進行中の解析を中断せず、次回の解析開始時から反映される旨の案内

#### 入力条件

- 対応形式：JPEG、PNG、WebP
- HEICはブラウザ対応差が大きいためMVP対象外とする。
- ファイルサイズ上限の初期値：20MB
- 画像の長辺上限：4096pxを目安に、推論前に適切な解像度へ縮小する。
- クリップボード貼り付けは画像入力領域にフォーカスがある場合だけ受け付ける。画像とテキストが同時に含まれる場合は画像だけを取り込む。
- 画像を含まない貼り付けは無視する。複数画像または複数ファイルが渡された場合は取り込まず、エラーを表示する。

### 6.2 画像調整画面

- 画像プレビュー
- 90度単位の回転
- 画像プレビュー上で直接移動・リサイズできる切り抜き領域
- 明るさ・コントラスト補正
- 元画像へ戻す
- 「解析開始」ボタン

切り抜き領域は選択範囲外を暗くし、境界線と四辺・四隅のハンドルを常時表示する。領域内部のドラッグで矩形全体を移動し、ハンドルのドラッグで各辺をリサイズする。マウス、タッチ、ペンをPointer Eventsで扱い、操作中はリアルタイムで表示へ反映する。操作箇所に対応するカーソルとキーボードフォーカスを表示し、タッチ用ヒット領域は44×44 CSS px以上とする。

枠とハンドルはキーボードでフォーカスできる。画像調整画面では、操作対象を事前に選択せず矢印キーを押すと領域全体を画面上の方向へ移動する。枠またはハンドルにフォーカスがある場合は、その対象を移動またはリサイズする。矢印キーでは元画像寸法の1%、Shift＋矢印キーでは5%ずつ調整する。明るさ・コントラストなど矢印キーを使う入力中は切り抜き操作へ割り当てない。領域は元画像内に制限し、幅と高さをそれぞれ元画像の20%以上に保つ。画像端または最小サイズを超える入力は境界値へクランプし、操作は継続する。

切り抜き領域は元画像座標で保持する。90度回転後も同じ元画像領域を維持し、プレビューと解析対象を一致させる。「元画像へ戻す」では回転、補正とともに切り抜き領域を画像全体へ戻す。

### 6.3 AI解析画面

- モデル取得進捗
- OCR進捗
- データ整形進捗
- キャンセル操作
- 推論時間が端末性能に依存する旨の表示
- メモリ不足時の対処案内

進捗は「準備中」「モデル取得中」「文字認識中」「データ整形中」「確認待ち」の段階で表示する。正確な残り時間は保証しない。
モデル取得中は、開発者コンソールへモデルファイル名、取得済み容量、総容量、割合を定期的に出力する。モデル取得後のONNXセッション初期化についても開始・完了を出力する。

解析失敗は、実行環境、画像準備、モデル取得・初期化、OCR、Gemma整形の工程別エラーコードで扱う。エラー画面には失敗工程、原因、「エラーコード」ラベル付きの公開エラーコード、推奨する復旧操作を表示する。OCR結果を取得済みのGemma失敗ではOCRを再実行せず、失敗した会話履歴を破棄してGemmaだけを再試行できるようにする。OCR失敗ではOCR再試行と画像調整への復帰を提供する。ユーザーによるキャンセルはエラー表示にしない。

診断情報は展開して表示およびコピーできるようにし、公開エラーコード、工程、選択モデル、再試行回数、ブラウザ種別、WebGPU可否、未知例外の短いメッセージだけを含める。アップロード画像、ファイル名、OCR本文、出演者名、Gemmaの生出力は含めない。

### 6.4 抽出結果確認画面

#### イベント情報

- イベント名
- 開催日（必須）
- タイムゾーン（初期値：Asia/Tokyo）
- 会場名
- 開場・開演時刻
- 注記

画像内に開催日が存在しない、または確定できない場合は、カレンダー出力前にユーザー入力を必須とする。

#### 予定一覧

画面は「元画像」「予定一覧」「選択予定の詳細」の3領域で構成する。一覧は時系列を維持し、「すべて」「要確認」「確認済み」で絞り込める。初期表示は「要確認」とする。狭い画面では一覧を常に表示し、元画像と詳細をタブで切り替える。

一覧には出演者名、種別、開始・終了時刻、ステージまたはブース、信頼度、確認状態を表示する。行を選択すると詳細編集パネルを表示し、対応する元画像の認識領域を強調する。開催日、相対時刻、属性、翌日指定を含む編集項目は詳細パネルに配置する。

詳細では以下を編集できるようにする。

| 項目 | 必須 | 説明 |
|---|---:|---|
| 出演者名 | 必須 | OCR結果を手動修正可能 |
| 種別 | 必須 | LIVE、特典会、物販、その他 |
| 開始時刻 | 条件付き必須 | 通常予定で必須 |
| 終了時刻 | 条件付き必須 | 通常予定で必須 |
| 相対時刻表現 | 任意 | 「終演後」など、時刻未確定の場合 |
| ステージ | 任意 | 複数ステージ型イベント用 |
| ブース | 任意 | A、B、Cなど |
| 撮影等の属性 | 任意 | 動画、静止画、モッシュ等 |
| 信頼度 | 表示のみ | high、medium、low |
| 確認状態 | 必須 | 未確認、確認済み |

#### 操作

- 行の追加・削除・複製
- 出演者名の一括置換
- LIVEと特典会の関連付け
- 元画像との並列表示
- 信頼度が低いセルの強調表示
- 「要確認」には未確認、低信頼、必須項目の入力不備、開始・終了時刻の矛盾がある予定を含める。
- 確認済みにできるのは、出演者名と開催日があり、開始・終了時刻または相対時刻が入力され、開始・終了時刻に矛盾がない予定だけとする。
- 一括確認操作には、操作前から確認可能な対象件数を表示する。
- 予定選択画面へ進めるのは、入力不備のない確認済み予定が1件以上ある場合だけとする。
- 未確認または入力不備の予定が残る場合、予定選択画面では対象外になることを遷移前に表示する。

## 7. AI処理仕様

### 7.1 画像前処理

1. EXIFの向きを補正する。
2. 長辺が上限を超える場合は縮小する。
3. ユーザー指定の切り抜きを反映する。
4. 必要に応じてコントラスト補正を行う。
5. 画像は領域分割せず、縮小後の画像全体を1回のOCR入力として処理する。

派手な背景や複数列を含む画像でも、行・列へ分割せず、画像全体のレイアウトと読み順を1回の推論で認識する。

複数ステージを含む場合、GLM-OCRには学習時と同じ公式タスクプロンプト `Table Recognition:` を使用し、同じ1回の推論内で画像全体の表構造を認識させる。独自の長文指示やJSON出力指示は使用せず、最大8,192出力トークンを確保する。出力された表全体を後段のGemma整形対象とし、左端のステージだけで完了扱いにしてはならない。

### 7.2 GLM-OCR出力

最低限、以下を取得する。

- 認識文字列
- 認識領域の座標
- 行またはブロックの順序
- 取得可能な場合は認識信頼度

元画像の座標と認識結果の対応を保持し、確認画面で該当領域を強調できるようにする。

### 7.3 Gemma整形

GemmaにはOCR結果と座標情報を渡し、JSON以外を返さないよう制約する。出力後はZodで検証し、不正な値を画面上で未確定として扱う。

Gemmaには正しいJSON出力の成功例をsystem promptで提示する。中間JSONは意味が明確な`event`と`schedules`をルートキーとする短い配列形式とし、`event`にはイベント情報1件だけ、`schedules`には予定行だけを格納する。アプリが`TimetableDocument`へ展開してID、タイムゾーン、確認状態、終了時刻の根拠、元画像領域を決定する。これにより、小型モデルによるルート項目の取り違えと、予定ごとのフィールド名の反復による出力上限到達を避ける。

初回応答がJSONとして解析・検証できない場合は、直前の会話履歴を引き継がない新しい会話を作り、成功例と同じJSON形式への変換を明示したプロンプトで1回だけ再実行する。生成途中で切れたJSONから完全な予定を安全に回収できる場合は再実行せず、不完全な末尾だけを破棄して確認画面へ進める。再実行後も解析・検証できない場合はエラーとして扱う。

OCRのHTML表セルまたはMarkdownステージ見出しから取得した全親ステージをGemmaの必須入力とする。Gemma出力にいずれかの親ステージが1件も含まれない場合は不完全な整形として扱い、欠落ステージを含む全見出しを明示して上記の再実行を行う。各予定のstageには親ステージを必ず含め、子列がある場合は`親 / 子`として保持する。

GLM-OCRがHTML表、またはステージ節と`時刻 | 名称`形式を返した場合、アプリはrowspan・colspanを含むセル位置を復元し、全画像OCR結果から`[名称, 開始, 終了, 親 / 子ステージ]`の短い候補配列を決定的に作る。Gemmaには長いHTMLやOCR全文を重複して渡さず、この全候補、全親ステージ見出し、イベント情報に必要な非予定セルだけを渡す。これによりGemmaのコンテキスト上限内で画像全体を整形対象にする。Gemmaが有効なJSON内で候補を省略しても、アプリはOCR候補を元画像領域付きの未確認予定として復元する。

中間JSONに、空のnotesを文字列`"[]"`で返す、または予定配列のbooth付近へ余分な`null`を1個挿入する既知の軽微な型ずれがある場合だけ、意味を変えずアプリ側で正規化する。それ以外の中間JSON不正を空予定へ変換して成功扱いにしてはならない。

Gemmaに次の判断を完全委任しない。

- 開催日の推測
- 日付をまたぐ時刻の確定
- OCRに存在しない出演者名の補完
- 「終演後」などからの架空時刻生成
- 認識不能な文字の断定

### 7.4 構造化データ定義

```ts
type Confidence = "high" | "medium" | "low";
type ScheduleType = "live" | "meet_and_greet" | "merch" | "other";

interface TimetableDocument {
  schemaVersion: 2;
  event: {
    name: string;
    date: string | null;       // 全項目へ適用する既定日。YYYY-MM-DD
    timezone: string;          // 例: Asia/Tokyo
    venue: string | null;
    openTime: string | null;   // HH:mm
    startTime: string | null;  // HH:mm
    notes: string[];
  };
  schedules: ScheduleItem[];
}

interface ScheduleItem {
  id: string;
  artist: string;
  type: ScheduleType;
  date: string | null;               // 複数日画像では項目ごとの開催日。YYYY-MM-DD
  startTime: string | null;
  endTime: string | null;
  endTimeSource: "explicit" | "manual" | "inferred_next_start" | "inferred_default" | "missing";
  endsNextDay: boolean;              // 終了時刻をイベント翌日として扱う
  relativeTimeLabel: string | null;
  stage: string | null;
  booth: string | null;
  attributes: Record<string, boolean | null>;
  confidence: Confidence;
  verified: boolean;
  sourceRegions: Array<{
    x: number;
    y: number;
    width: number;
    height: number;
  }>;
}
```

- 1枚に複数日が含まれる場合は `ScheduleItem.date` を使い、各列・各枠を画像内の日付へ対応付ける。
- 画像内の年表記と月日表記が別領域にあっても、同一イベントの明示情報として対応が取れる場合は組み合わせてよい。画像内に年がない場合は推測せず、ユーザー入力を求める。
- ステージ見出しが親子構造の場合は `親 / 子` の順で保持する。名称の大文字小文字、記号、空白は可能な限り画像表記を維持し、モデル知識から正式名称を補完しない。
- 時刻と名称を持つ独立枠はライブ以外も `other` として抽出する。開場・開演はイベントメタデータとして扱い、出演枠にはしない。
- 終了時刻が明記されている場合は `explicit` とする。欠けている場合、同一日・同一ステージの次枠が60分以内なら次枠開始を候補とし、それ以外は開始60分後、最終枠は開始30分後を候補にする。候補は確定情報ではなく、ユーザーが個別確認するまでCalendar登録対象外とする。

### 7.5 検証ルール

- 時刻は24時間表記の `HH:mm` に正規化する。
- 終了時刻が開始時刻以前の場合は警告する。ただし日付またぎをユーザーが指定した場合を除く。
- 開催日、開始時刻、終了時刻のいずれかがない予定は、カレンダー登録対象から初期状態で除外する。
- 推定終了時刻を持つ予定は、ユーザーが個別確認するまでカレンダー登録対象から除外する。
- `low` の項目はユーザーが確認するまでエクスポート時に警告する。
- 同一出演者、同一種別、同一時間の重複行を検出する。
- AI出力に含まれる未知のHTMLやMarkdownを描画しない。

## 8. モデル管理

### 8.1 初回取得

- 解析開始前にモデル名、容量、配信元を表示する。
- ユーザー操作後にのみ大容量ダウンロードを開始する。
- ダウンロード進捗と中止操作を提供する。
- CORSとRange Requestに対応する配信元を使用する。

### 8.2 モデルキャッシュ

- AIモデルの再ダウンロードを避けるため、モデル本体に限りCache Storageへキャッシュする。
- IndexedDBは使用しない。
- アップロード画像、OCR結果、整形済みデータ、選択内容はキャッシュしない。
- モデルID、量子化方式、バージョン、チェックサムを記録する。
- モデル更新時は別バージョンとして取得し、正常取得後に旧キャッシュを削除可能にする。
- 設定画面からモデルキャッシュを削除できるようにする。

### 8.3 メモリ対策

- GLM-OCR終了後、Gemmaロード前に不要なTensorや画像バッファを解放する。
- 可能であれば両モデルを同時常駐させない。
- Web Worker内で推論し、メインUIの停止を防ぐ。
- WebGPUデバイス喪失やメモリ不足を捕捉し、画像解像度を下げる再試行方法を案内する。

## 9. タイムライン生成仕様

### 9.1 レイアウト

- 時刻を一定の縮尺で配置する。
- LIVE、特典会、物販を視覚的に区別する。
- 同時刻の予定は並列表示する。
- 重複予定には警告アイコンを表示する。
- 時刻未確定の予定はタイムライン末尾の「時刻未確定」領域へ表示する。

### 9.2 出力

- SVGはベクターデータとして保存する。
- PNGはユーザー指定の倍率で書き出す。
- ファイル名の初期値は `{event-name}-{date}-my-timetable` とする。
- 出力画像へ元画像を自動転載しない。ユーザーが選択した情報から新規デザインを生成する。

## 10. カレンダー連携

### 10.1 ICS出力

MVPの標準方式とする。Googleログインを必要とせず、Google Calendar、Apple Calendar、Outlookなどへ取り込めるファイルを生成する。

各予定に以下を設定する。

- 件名：`出演者名 - LIVE` など
- 開始・終了日時
- タイムゾーン
- 場所：ステージまたはブース
- 説明：イベント名、種別、注記
- UID：イベント・出演者・開始時刻から安定して生成

### 10.2 Google Calendar直接登録

- Google Identity Servicesを用いたブラウザ向けOAuth 2.0を使用する。
- Google Cloud ConsoleでOAuthクライアントIDを作成する。
- GitHub Pagesの本番URLをAuthorized JavaScript originsへ登録する。
- クライアントIDは公開情報としてフロントエンドへ設定可能だが、クライアントシークレットは使用・埋め込みしない。
- 必要最小限のCalendarスコープを選択する。
- アクセストークン取得後、ブラウザからGoogle Calendar APIの `events.insert` を呼び出す。
- 複数予定の登録前に明示的な最終確認を表示する。
- 一括登録中に一部が失敗した場合、予定ごとに成功・失敗を表示し、失敗分だけ再実行できるようにする。
- OAuth設定未完了または利用不能時も、ICS出力は常に利用可能にする。

Google CalendarのOAuth審査・公開設定はアプリの配布範囲と使用スコープに依存するため、一般公開前にGoogleの最新要件を確認する。

## 11. ローカル保存

### 11.1 基本方針

- IndexedDBは使用しない。
- アップロード画像、画像のプレビュー、OCR生データ、Gemmaによる整形結果、ユーザーの修正内容、出演者の選択状態、生成したタイムラインを永続保存しない。
- 作業データはJavaScriptのメモリ内だけで保持する。
- ページの再読み込み、タブを閉じる操作、またはブラウザ終了により作業データを破棄する。
- ページ再読み込み前には、未出力の作業内容が失われることを確認する警告を表示する。
- 前回使用した画像やタイムテーブルを次回アクセス時に復元しない。

### 11.2 localStorage

localStorageには、アプリを利用するための必要最小限の設定だけを保存する。

| キー例 | 内容 | 初期値 |
|---|---|---|
| `ui.theme` | light、dark、system | system |
| `ui.language` | 表示言語 | ja |
| `ui.gemmaModel` | Gemma 4の選択モデル（e2b、e4b） | e2b |

タイムゾーン、移動時間バッファ、出力サイズ、イベント情報、履歴などは保存せず、アクセスごとに初期値へ戻す。今後localStorage項目を追加する場合も、アプリの基本表示に継続して必要な設定だけに限定する。

保存済みのE4Bが現在のWebGPU・端末メモリ要件を満たさない場合はE2Bへフォールバックし、保存値もE2Bへ更新する。

#### 11.2.1 表示言語

- 対応言語は日本語（`ja`）と英語（`en`）とする。
- 初回表示時は `localStorage["ui.language"]`、`navigator.languages` / `navigator.language`、日本語の順に表示言語を決定する。未対応の言語コードは候補から除外する。
- ブラウザから自動検出した言語は保存しない。ヘッダーの言語ボタンからドロップダウンを開き、ユーザーが言語を明示的に選択する。言語変更が成功した場合だけ `ui.language` へ保存する。
- 言語変更は現在の画面へ即時反映し、アップロード画像、抽出結果、修正内容、選択状態、タイムライン設定を維持する。`<html lang>` は解決済みの表示言語と常に一致させる。
- 見出し、説明、操作、フォームラベル、placeholder、アクセシブル名、エラー、警告、確認ダイアログ、予定種別、日時・数値・件数を表示言語へ切り替える。
- SVG・PNGへ含める表示文言とGoogle Calendarへ登録する説明文は、出力または登録操作時の表示言語を使う。ICSの機械可読な日時形式はロケールに依存させない。
- イベント名、出演者名、OCR結果などのユーザーデータは翻訳しない。UI言語の変更によってOCR対象言語やイベントのタイムゾーンを変更しない。
- 翻訳リソースはアプリの静的アセットとして配信し、翻訳リソース、アップロード画像、抽出結果、ユーザーデータを外部翻訳サービスへ送信しない。

### 11.3 Cache Storage

- Cache StorageはGLM-OCRおよびGemmaのモデルファイルだけに使用する。
- ユーザーがアップロードした画像や生成データには使用しない。
- モデルキャッシュを削除する操作を設定画面に設ける。
- モデルキャッシュを削除してもUIテーマと言語設定には影響しない。

### 11.4 認証情報

- Google OAuthのアクセストークンはメモリ内だけで保持する。
- localStorage、Cache Storage、Cookieへアクセストークンを保存しない。
- ページ終了またはトークンの有効期限切れで破棄する。

### 11.5 設定の削除

設定画面に以下の操作を設ける。

- UI設定を初期値へ戻す
- AIモデルのキャッシュを削除する

保存済みプロジェクト一覧、前回作業の復元、画像履歴、解析履歴は提供しない。

## 13. 非機能要件

### 13.1 操作性

- スマートフォン表示に対応するが、AI解析はPC推奨と明示する。
- AI処理中も画面が操作不能にならない。
- 主要操作はキーボードでも実行可能にする。
- 色だけに依存せず、文字やアイコンでも状態を示す。

### 13.2 性能

- 初期画面ではAIモデルを読み込まない。
- AI関連コードは遅延ロードする。
- 大容量モデルはユーザー操作後に読み込む。
- 推論時間の数値目標は、採用モデルと最低対象端末を確定した後に実機計測して設定する。

### 13.3 可用性

- AI処理に失敗しても、予定を手入力してタイムラインを作成できる。
- Google連携に失敗してもICSを出力できる。
- ページ再読み込み時に作業データを復元せず、安全に初期状態へ戻る。

### 13.4 アクセシビリティ

- WCAG 2.2 AAを目標とする。
- フォーム要素へラベルを付与する。
- フォーカス状態を視認可能にする。
- エラー箇所と修正方法をテキストで示す。

## 14. エラー仕様

| 状況 | 表示・対処 |
|---|---|
| WebGPU非対応 | 推奨ブラウザを案内し、手入力モードを提供 |
| モデル取得失敗 | ネットワークと空き容量を案内し再試行 |
| CORSエラー | 配信元障害として表示し、別モデル配信元を選択可能にする |
| メモリ不足 | 画像解像度の縮小、他タブ終了、軽量モデル選択を案内 |
| OCR結果なし | 切り抜き・回転・補正または手入力を案内 |
| JSON検証失敗 | 不正項目を未確定として編集画面へ表示 |
| 日付未入力 | カレンダー出力前に入力を要求 |
| OAuth拒否 | 登録を中止し、ICS出力を案内 |
| Calendar一部失敗 | 成功・失敗を個別表示し、失敗分のみ再実行 |

## 15. テスト方針

### 15.1 OCR評価用画像

- 単色背景の表
- 派手な背景と縁取り文字を含む表
- 縦長・横長画像
- 複数ステージ
- 日本語・英数字混在
- 低解像度または圧縮済み画像
- ○×などの記号列
- 「終演後」などの相対表現

### 15.2 必須テスト

- AI出力がスキーマ外でも画面が壊れないこと
- 元画像と抽出セルの対応が表示できること
- 時間重複が正しく検出されること
- SVGとPNGの文字切れがないこと
- ICSを主要カレンダーで読み込めること
- OAuthキャンセル後にトークンが残らないこと
- Pagesのサブパス配信でアセットが正しく取得できること
- 再読み込み後に前回の画像、OCR結果、選択内容が表示されないこと
- localStorageにテーマ、言語、Gemma選択モデル以外の作業情報が保存されないこと

## 16. GitHub Pagesデプロイ要件

- `vite.config.ts` の `base` を `/REPOSITORY_NAME/` に設定する。
- GitHub Actionsで依存関係の取得、テスト、ビルド、Pages公開を行う。
- OAuth本番Originは `https://OWNER.github.io` を登録する。
- カスタムドメインを使用する場合は、そのOriginもGoogle側へ登録する。
- モデル配信元のCORS、Content-Type、キャッシュヘッダーを確認する。
- AIモデルのURLとバージョンは設定ファイルで切り替え可能にする。
- Content Security Policyの導入を検討し、モデル配信元とGoogle API以外への接続を制限する。

## 17. 受け入れ条件

MVP完成の条件を以下とする。

1. GitHub Pages上でアプリが表示・操作できる。
2. 対応PCで画像を外部送信せず解析できる。
3. GLM-OCR結果をGemmaが所定のJSON形式へ整形できる。
4. ユーザーが全項目を修正できる。
5. 選択した出演者だけのタイムラインを生成できる。
6. SVGとPNGを保存できる。
7. 正しい日時を持つICSを保存できる。
8. OAuth設定済み環境ではGoogle Calendarへ登録できる。
9. 認識失敗時でも手入力で全機能を利用できる。
10. APIキー、クライアントシークレット、アクセストークンを静的ファイルへ保存しない。

## 18. 主なリスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| ブラウザ版GLM-OCRの互換性不足 | OCRを実行できない | 技術検証を最初のマイルストーンとし、手入力モードを常設 |
| モデル容量が大きい | 初回表示・解析が遅い | 遅延取得、量子化、キャッシュ、容量事前表示 |
| GPUメモリ不足 | クラッシュ・推論失敗 | モデルを順次ロード、画像縮小、軽量モデル選択 |
| 装飾文字の誤認識 | 誤った予定作成 | 元画像対照、信頼度表示、登録前確認 |
| AIによる値の創作 | 架空の時刻・出演者 | スキーマ検証、推測禁止、未確定値を許容 |
| 外部モデル配信元の停止 | 新規端末で解析不可 | 配信元切替設定、バージョン固定、チェックサム確認 |
| Google OAuth設定の複雑さ | 直接登録不能 | ICSを標準機能として維持 |
| GitHub Pagesの帯域・容量制限 | モデル配信に不適 | モデルをPages外の静的配信元に置く |

## 19. 開発マイルストーン

### Phase 0：技術検証

- 対象ブラウザでGLM-OCR変換モデルをロードする。
- 添付例相当の画像から文字と行・列対応を取得する。
- Gemma E2BでJSON整形を行う。
- 2モデルを順次実行した際のメモリ使用量を測定する。

Phase 0が成立しない場合は、「画像認識をブラウザ内の別OCRへ変更する」または「手入力中心へ縮小する」判断を行う。

#### Phase 0技術判断（2026-08-27）

- `Ji-Ha/glm-ocr-onnx` はORT Web用manifestを含むが、完全ブラウザ構成の推定モデル常駐量が約18.25GBであり、MVPの一般対象端末では実用的でない。
- `brad-agi/glm-ocr-onnx-webgpu` は全int8で約1.77GBまで縮小され、KV版グラフも公開された。しかし実モデルをONNX Runtimeで検査すると、`prefill_int8.onnx` と `decode_int8.onnx` の `logits` 出力は語彙数59,392ではなくhidden size 1,536であり、公式設定も `tie_word_embeddings: false` である。非共有のLM headが同梱されていないため、この成果物だけでは正しい自己回帰生成を完結できない。
- Phase 1はHugging Face公式Transformers.js担当者が変換・公開した `onnx-community/GLM-OCR-ONNX` を採用する。q4のvision encoder、token embedding、merged decoderをTransformers.js経由のONNX Runtime Web / WebGPUで実行し、モデル取得量を約750MBに抑える。
- Tesseract系フォールバックは使用しない。WebGPU非対応またはGLM-OCR失敗時は手入力モードを提供する。
- 構造化処理はLiteRT-LM Web APIを使用する。初期値は `gemma-4-E2B-it-web.litertlm` とし、対応端末では `gemma-4-E4B-it-web.litertlm` を選択可能にする。

### Phase 1：データ編集と選択

- 画像アップロード・調整
- OCR・整形処理
- 結果確認・手動修正
- 出演者選択・重複検出

### Phase 2：エクスポート

- SVG/PNGタイムライン
- ICS出力
- 最小限のUI設定保存

### Phase 3：Google連携と品質向上

- Google OAuth
- Calendar直接登録
- OCR領域表示
- アクセシビリティ・実機検証

## 20. 最終判断

本構成は実装可能だが、最大の不確定要素はGitHub Pagesではなく、ブラウザ変換版GLM-OCRの互換性、モデル容量、推論速度、GPUメモリである。そのため、画面開発より先にPhase 0の実機検証を行う。

アプリ構成にはReact + Vite + TypeScriptを採用する。GitHub Pagesと単一ページアプリの相性がよく、Next.jsのサーバー機能を利用しない本要件では構成が単純になるためである。Calendar連携はICSを標準とし、Google Calendar直接登録を追加機能として扱う。
